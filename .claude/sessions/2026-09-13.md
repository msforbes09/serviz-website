## v1 sideways scroll on phones

Branch `fix/v1-mobile-sideways-scroll` off `origin/develop`.

### What shipped

- `app/8sfz8dn5ts/layout.tsx`: the `v1-root` wrapper carries `overflow-x-clip`.
- `app/8sfz8dn5ts/layout.test.tsx`: renders the layout and asserts the clip
  class. First test under `app/`; it mocks `next/font/google`, which is not
  callable outside the Next compiler.

### Root cause

Two entrances park elements past the right edge of the viewport before
sliding them in: the hero photo (`.enter-x`, `--from-x: 56px`, plus the orange
block hanging 12px further) and each FAQ card (`.reveal-x`, `--from-x: 48px`).
A transformed element still counts toward the document's scrollable area, so
on a 440px phone the page was 484px wide on first paint and 464px wide until
the FAQ revealed. The page could be dragged sideways, and mobile Chrome widened
its layout viewport to match, which made the sticky nav look narrower than
the screen. Desktop never showed it because the wide margins swallowed the
offsets.

### Why clip and not hidden

`overflow-x: hidden` would make the wrapper a scroll container and unstick the
nav. `clip` only clips paint and scrollable overflow, so the sticky nav and the
fixed menu overlay are untouched. Checked in the in-app browser at 440px:
scroll width stays 440 across the whole page, nav sticks at full width.

### Gotcha

`vi.mock("next/font/google", ...)` is needed for any test that imports a
module calling the font loaders. Return `{ variable, className }` from each.

### What shipped

- `RevealController` is mounted as the last child of each page (all five v3
  pages and the v1 page), not in the layouts. The first cut this morning put
  it in the layout with a `usePathname()` dependency; the mobile pass below
  found that caused a hydration mismatch on nested pages. Both the pathname
  dependency and the v3 layout test were removed with it; the guard is now
  `components/motion/reveal-mount.test.ts`, a source check on the six pages
  and two layouts.
- No v3 call site changed: the JS rules read the same `.reveal`, `.reveal-x`,
  `.reveal-step`, `--i` and `--from-x`.

### Gotchas

- **The controller does not arm on a page with no `.reveal` element.** A
  layout test that renders `{null}` children asserts `data-reveal-ready` and
  fails for that reason, not because the controller is missing. Give it one
  target.
- **HMR keeps stale console errors.** The dev server compiled the tree while
  conflict markers were still in `globals.css`; those errors stayed in the
  console after the fix. Judge by whether the count grows on a reload.

### Verified

Lint, typecheck, 88 tests. In the browser: home scrolled, then client
navigation to About and to Services, then a fresh load of News. On every
page `data-reveal-ready` was set and no in-view reveal was left hidden.

## v3 mobile pass

Same branch. Four fixes, all recorded in `TODO.md` under "v3 mobile pass":
the closed mobile menu leaking 17px of the active link, the contact map
widening the page through aspect-ratio min-size transfer, the services intro
column sticky in a single column, and the controller's hydration race, fixed
by mounting it per page.

### Gotchas

- **In a hidden Browser pane, scroll events and IntersectionObserver
  callbacks do not fire at all.** Both run in the rendering steps, which a
  hidden document skips. Rects still resolve. So a scroll-stop sweep never
  runs there and reveal counts read zero; dispatch `visibilitychange` to
  force a sweep when checking the controller from a hidden pane.
- **Next 16 keeps visited and prefetched pages in the DOM** inside hidden
  Activity boundaries. Element counts include them; filter with
  `checkVisibility()`.
- **After editing a component, the first hard load of each page recompiles
  and can take several seconds.** A 3s wait was not enough; measurements
  taken then saw the loading state.
- `CLAUDE.md` now says session notes are read only when the user asks.
